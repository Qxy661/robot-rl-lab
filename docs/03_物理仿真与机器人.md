# 03 · 物理仿真与机器人

前两章一直在说"环境"，但没说这个环境是哪来的。这一章回答它，并且讲清机器人
控制里最基础的一件事：**PD 控制**——理解了它，才能理解为什么本项目让策略输出
关节角度而不是力矩。

## 为什么一定要用仿真

训练一个行走策略需要几百万步交互。每一步在真机上意味着一次电机指令、一次传感器
读数，还有一次摔倒的风险。

真机上跑一百万步，按每秒 50 步算要五个多小时，而这期间机器人一直在摔——电机
和结构件的损耗、电池的消耗、总要有人扶起来。更要命的是**训练初期策略是随机的**，
它只会乱挥关节，真机撑不过几十秒。

仿真里这些都消失了：摔倒就是复位，几百万步一个晚上跑完，还能同时开几十个机器人
一起跑。所以业界的做法统一是：**在仿真里训到收敛，再想办法挪到真机上**。
后者就是所谓 sim2real，本章最后讲。

## MuJoCo 是什么

MuJoCo 是一个物理引擎，输入是机器人模型，输出是它的运动。它算的事包括：关节
在力矩下怎么转、脚踩在地上受力多少、身体撞到东西会怎样。

选它的理由很实际：

- `pip install mujoco` 就能用，不需要 GPU，Windows / macOS / Linux 全支持
- 计算精度高、接触处理稳，学界和工业界都在用
- 配套的 [MuJoCo Menagerie](https://github.com/google-deepmind/mujoco_menagerie)
  提供了官方维护的机器人模型，本项目的 G1 / H1 / Go2 都来自那里

Isaac Lab 那套基于 GPU 的仿真在规模上更强（几千个环境并行），但它的仿真器不开源、
只能在 Linux + NVIDIA 显卡上跑，也更重。对一个要能被任何人 clone 下来就跑的项目，
MuJoCo 是更合适的地基。

## 模型文件：机器人长什么样

MuJoCo 用 XML 描述机器人，这个格式叫 MJCF。一个关节长这样：

```xml
<joint name="left_knee_joint" type="hinge" axis="0 1 0" range="-0.09 2.87"/>
```

翻译过来是：这里有个叫"左膝"的关节，绕着 y 轴转，能转的角度在 -0.09 到 2.87
弧度之间。

执行器（actuator，也就是电机）长这样：

```xml
<actuator>
  <position name="left_knee" joint="left_knee_joint" kp="150" kv="4"
            ctrlrange="-139 139"/>
</actuator>
```

一个 `<position>` 执行器接受一个目标角度，自己算出要出多大力——这正是下一节要
讲的 PD 控制。

## PD 控制：机器人关节的通用控制方式

假设你想让膝关节停在 0.5 弧度。最简单的方法是：偏得越多，就使得劲越大。

```
力矩 = kp × (目标角度 − 当前角度) − kd × 当前角速度
```

两项各管一件事：

- **比例项 kp**：差得越远，回得越快。但只有它的话，关节会冲过头然后来回震荡——
  就像开车只看距离不看速度，一定会追尾。
- **微分项 kd**：转得越快，刹车越狠。它提供阻尼，把震荡压下去。

`kp` 和 `kd` 的取值就是这两个力的强度。调参的经验是：kp 决定跟得多紧，kd 通常取
kp 的 1/50 到 1/20 之间。

MuJoCo 的 `<position>` 执行器内部就在做这个计算。你在 `RobotSpec` 里看到的
`pd_kp` / `pd_kd` 会写进模型的执行器里。

### 为什么不让策略直接输出力矩

这是本项目一个关键的架构选择。

理论上策略可以直接输出力矩，端到端学习。但实践中这么做有几个问题：力矩对姿态的
影响是二阶的（力矩 → 加速度 → 速度 → 位置），策略要学的东西更绕；力矩输出不稳
时关节会剧烈震荡；而且真机上的底层控制器本来就是位置控制，输出位置更好对接。

所以主流做法是分层：

```
策略（神经网络）      决定"想去哪个姿态"      50Hz
    ↓ 目标关节角度
PD 控制器             决定"出多大力气过去"     1000Hz
    ↓ 力矩
电机
```

这样策略学的是一个简单得多的问题。这个分层是本项目动作契约的由来：**动作是关节
目标角度的增量，不是力矩**。

## 仿真是怎么算的

MuJoCo 内部两个核心对象：

- `mjModel`：模型本身。关节数、质量、几何形状、执行器参数。**只读**，训练全程
  不变，可以被多个环境实例共享。
- `mjData`：仿真状态。当前每个关节的角度和速度、机身在空间中的位置姿态、接触力。
  **每个环境实例都需要自己的一份**。

推进仿真就一行：

```python
mujoco.mj_step(model, data)
```

它内部做的事：读取 `data.ctrl`（你写的控制量）→ 算力矩 → 算加速度 → 积分出新的
位置和速度 → 处理碰撞和接触。

三套数组需要分清楚：

| 数组 | 装什么 | 例子 |
| --- | --- | --- |
| `qpos` | 所有关节的位置 | 每个铰链关节一个角度 |
| `qvel` | 所有关节的速度 | 每个自由度一个角速度 |
| `ctrl` | 执行器的控制输入 | 每个执行器的目标角度或力矩 |

### 自由关节与浮动基座

人形机器人的躯干在空间中有 6 个自由度——三个方向的平移和三个方向的旋转。在 MJCF
里这由一个 `free` 关节表示："浮动基座"（floating base）。机器人能走路、能摔倒，
靠的就是它。

代价是 `qpos` 和 `qvel` 的维度对不上：一个自由关节在 `qpos` 里占 7 格（3 个位置
+ 4 个四元数，用四元数表示旋转），在 `qvel` 里占 6 格（3 个线速度 + 3 个角速度）。

所以从 `qpos` 里找某个腿部关节的角度，不能想当然地按序号对。**这个映射必须显式
建立**，本项目把它放在 `robotrl/assets/loader.py` 里：

```python
@dataclass
class RobotModel:
    actuator_ids: np.ndarray   # 被控关节对应的执行器索引
    qpos_ids: np.ndarray       # 被控关节在 qpos 中的位置
    dof_ids: np.ndarray        # 被控关节在 qvel 中的位置
    ...
```

映射错位的后果很隐蔽：仿真照跑、不报错，只是策略学不会。所以映射在加载时就确定
好，而且有测试专门验证它指向正确的关节。

### 冻结关节的处理

G1 全身 29 个自由度，本项目只控制 15 个，手臂的 14 个不管。

不管不等于放着。没有控制信号的关节在地心引力下会瘫软下来乱甩。做法是**照样给它
一个目标角度**（模型里定义好的默认姿态），让 PD 控制器把它锁住，只是这个目标不
来自策略。

这就是 `RobotModel.held_actuator_ids` 和 `held_targets` 的用途。

## 从仿真到真机：sim2real gap

在仿真里训好的策略直接搬到真机上，通常表现会明显变差，有时直接摔。原因是仿真和
现实之间有差距，主要来自几处：

- **执行器差异**：真电机的响应有延迟、有力矩上限、有摩擦，仿真里的 PD 是理想的
- **摩擦与地面**：仿真里地面是理想刚体，真机的地面会打滑、会下陷
- **质量与惯量**：真机装配上电池、外壳、线束后质量分布和模型有偏差
- **传感器噪声**：仿真里角度是精确的，真机编码器有噪声、IMU 有漂移

缩小这个差距的方法主要两类。

**域随机化**（domain randomization）：训练时不去追求"精确模拟真机"，而是**故意
让参数在一个范围内随机变化**——摩擦系数随机、质量随机、电机强度随机、PD 增益
随机、偶尔推机器人一把。策略见过了足够宽的分布，真机落在分布的哪里都能应付。

这是本项目 `EventsConfig` 里那些随机化项的作用，实现在
`robotrl/envs/events.py`。

**系统辨识**：反过来，精确测量真机的参数，把仿真调到与真机一致。这个方法更精确，
但需要专门的实验设备，成本高。本项目用的是域随机化这条路线——它在没有真机的情
况下也能做，而且效果通常更稳健。
