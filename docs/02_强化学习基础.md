# 02 · 强化学习基础

上一章的网络需要一个前提：有一批"输入和正确答案"的数据。教机器人走路时，
这个前提不成立——没人能写出"此刻左膝关节应该转到 0.37 弧度"这种标准答案。

强化学习解决的就是这个问题：**没有标准答案，只有结果好坏的时候，怎么学。**

## 和监督学习的根本区别

想象教一个人骑车。

监督学习的教法是：给他一千段视频，每一帧都标注"车把应该往左偏 3 度"。这需要
一个会骑车的人逐帧标注，而且标注的结果未必最优。

强化学习的教法是：让他自己骑，摔了就扣分，稳住了就加分。他不知道自己哪一步做
对了，只知道这一趟整体表现如何。反复试，慢慢就找到了门道。

后者更接近真实的学习过程，也更适合控制问题——**因为我们往往说不清"正确的
控制量"是多少，但很容易判断"结果好不好"**。

## 那个循环

强化学习的全部结构就是下面这个循环：

```
        ┌──────────── 动作 a ────────────┐
        ▼                                │
     ┌──────┐                       ┌──────────┐
     │ 策略 │                       │   环境   │
     └──────┘                       └──────────┘
        ▲                                │
        └──── 观测 s, 奖励 r ─────────────┘
```

每一时刻发生四件事：

1. 策略看到当前状态 s，决定动作 a
2. 环境因这个动作发生变化，进入新状态
3. 环境给出一个奖励 r，评价刚才那一下做得好不好
4. 策略拿到新的观测，重复

对应到本项目的代码，就是 `robotrl/envs/base_env.py` 里那个 `step()`：

```python
result = env.step(action)     # 动作进去
result.obs                    # 新观测
result.reward                 # 这一步的奖励
```

这个循环在本项目里每秒跑 50 次。也就是每 20 毫秒，策略网络要完成一次
"看观测 → 算动作 → 输出关节目标"。这个频率不是随便定的，后面会讲。

## 五个核心概念

**状态（state）**：机器人此刻的完整情况——关节角度、关节速度、机身姿态、机身
速度。现实中拿不到完整的真实状态，只能拿到带噪声的观测（observation）。项目里
统一叫 obs。

**动作（action）**：策略的输出。本项目的动作是**每个关节的目标角度增量**，不是
力矩。这个选择很关键：让上层策略管"想去哪个姿态"，下层用 PD 控制器管"怎么用力
到达那个姿态"。分工之后策略要学的东西简单得多。

**奖励（reward）**：一个数字，评价这一步。这是**唯一**告诉策略"什么算好"的
信号。设计奖励是强化学习里最需要人的判断力、也最容易出错的地方——奖励写歪了，
策略会精准地学会你没想让它学的东西。

**策略（policy）**：从观测到动作的映射函数。它就是上一章那个神经网络。所谓
"训练一个机器人"，实质是**调整这个网络的参数**。

**回报（return）**：从当前时刻开始，往后所有奖励加起来。

```
回报 = r₁ + r₂ + r₃ + ... + r_T
```

策略的目标不是让眼前这一步奖励最大，而是让**长期累积**最大。

## 折扣：未来的奖励要打折

实际用的是折扣回报：

```
回报 = r₁ + γ·r₂ + γ²·r₃ + ...    (0 < γ < 1)
```

`γ`（gamma）通常取 0.99，意思是每往后一步，奖励的价值打 1% 的折。

为什么要打折？两个原因。一是**当下更确定**：十秒后的收益远不如现在拿到的实在，
而且中途可能摔倒，后面的奖励根本拿不到。二是**数学上的收敛性**：不打折的话，
只要任务能无限进行下去，回报可能是无穷大，没法比较优劣。

## 价值函数：预测未来能拿多少分

策略需要知道"现在这个状态好不好"，才能决定往哪走。于是引入一个辅助函数：

**状态价值 V(s)**：从状态 s 出发，按当前策略走，预期能拿到的折扣回报。

有了它，策略的改进方向就清晰了：在状态 s 做动作 a，如果之后的状态 s' 的价值
比现在高，那这个动作就是好的。

价值函数也需要用神经网络拟合，这就是所谓的 **critic（评论家）**，而输出动作的
网络叫 **actor（演员）**。本项目 PPO 里的 `ActorCritic` 就是这两个网络的组合。

一个实用细节：critic 可以比 actor 看到更多信息。因为 critic 只在训练时用到、
不会部署到真机上，所以可以"作弊"——直接给它机身的真实速度、地形高度、摩擦系数
这些策略拿不到的量。它价值估计得更准，反过来让 actor 学得更好。这叫
**asymmetric actor-critic**，本项目默认开启（配置里的 `use_privileged_critic`）。

## 探索与利用

一个绕不开的矛盾：

- **利用**：已知左边那条路得分高，那就一直走左边
- **探索**：但右边还没试过，说不定更高

只利用不探索，会卡在次优方案上；只探索不利用，永远在乱试。

做法是让策略带有随机性。PPO 的做法是让网络输出一个高斯分布的均值和标准差，
每次从分布里采样一个动作：

```python
mean, std = policy(obs)
action = mean + std * random_noise      # 采样
```

训练初期 std 较大（多探索），随着训练进行逐渐变小（多利用）。评估时不用采样，
直接取均值——这样同一个策略每次评估表现一致，结果可复现。

SAC 走得更远，它把"探索"写进了目标函数：除了最大化回报，还要求策略保持一定的
随机性（熵）。好处是探索行为是自动调节的，两个算法的详细对比见 04 章。

## 观测、动作、奖励在本项目里的具体形式

看 `robotrl/contracts.py` 里的观测契约，策略每步看到的是这些：

```
lin_vel      3 维    机身线速度（前后、左右、上下）
ang_vel      3 维    机身角速度（滚转、俯仰、偏航）
proj_gravity 3 维    重力方向在机体系下的投影——这一个量就表达了机身倾斜程度
cmd          3 维    指令：期望的前进速度、侧移速度、转向角速度
dof_pos      n 维    各关节角度与默认姿态的差
dof_vel      n 维    各关节角速度
last_action  n 维    上一步的动作
```

前 12 维与机器人形态无关，任何机器人都一样。后三段长度随关节数变化——四足 12
维、G1 人形 15 维，所以总维度是 `12 + 3n`。

把首尾对齐是有意为之：**固定段的下标在所有形态上一致**，这样部署层做误差归因
时不用为每种机器人写一套索引。

至于动作：n 维，每个关节一个目标角度增量，取值范围 `[-1, 1]`，然后由环境换算成
实际关节角：

```
目标角度 = 默认姿态 + 缩放系数 × 动作
```

把动作限制在 `[-1, 1]` 有两个好处：动作尺度与具体机器人解耦（换机器人不用改网络
输出层），以及导出的 ONNX 天然带了输出范围约束，量化时不用再补裁剪。

## 奖励设计：教机器人走路的真正难点

看本项目速度跟踪任务的奖励构成（`robotrl/envs/tasks/velocity.py`），它不是一项，
而是一组：

| 奖励项 | 作用 | 常见权重 |
| --- | --- | --- |
| 线速度跟踪 | 主体目标：跟上指令速度 | +1.0 |
| 角速度跟踪 | 转向跟上指令 | +0.5 |
| 姿态平直 | 机身保持水平 | -2.0（惩罚倾斜） |
| 高度保持 | 身体不要蹲下去或跳起来 | -1.0 |
| 动作变化率 | 让输出平滑，别抖 | -0.01 |
| 关节速度惩罚 | 别转太快 | -0.001 |
| 力矩惩罚 | 省电，同时避免暴力动作 | -0.0002 |
| 足端滑动 | 脚落地时别打滑 | -0.05 |

正项是"要做的事"，负项是"别做的事"。**只有正项会导致机器人学会用各种奇怪的
姿势骗分**——比如为了速度目标一直向前扑。负项把这些歪路堵上。

这套设计是多年积累的经验，不是从原理推出来的。这类奖励项在业界已经相当标准化，
本项目列出的也是通行做法。真实的调参过程仍然需要反复试。

## 为什么是 50Hz

控制频率决定了两件事：策略每秒钟要做多少次决策，以及单次决策最多能花多少时间。

选 50Hz 的原因是平衡：

- 定得太低（比如 10Hz），重心偏移来不及修正，机器人会晃
- 定得太高（比如 1000Hz），神经网络推理时间不够，而且相邻两步的观测几乎一样，
  学不到新东西

50Hz 意味着每步 20 毫秒。而物理仿真用 500Hz（`sim_dt=0.002`）跑，因为接触
碰撞这类刚性约束需要更细的积分步长才稳定——**一个控制步内部跑 10 次物理积分**，
这个比值在配置里叫 `decimation`。

## 一次训练大概是什么样

把上面串起来，本项目训练一次的主循环是这样的：

```
重复很多次：
    用当前策略跑 N 个环境、每个跑 M 步，收集 (观测, 动作, 奖励, ...)
    从这批数据算回报和价值目标
    用这些数据更新网络参数（上一章那五步）
    定期评估，记录曲线
```

单次循环收集的数据量叫一个 batch，跑完整个训练通常是几百万到上千万步。

时间花在两个地方：物理仿真和网络更新。仿真那部分能并行——一次控制步要推进 N 个
环境，每个环境的物理计算互不依赖。本项目的实测：G1 任务单环境每步约 1.5 ms，
串行推进 64 个环境要 96 ms 一个控制步；改成把整批环境交给多个子进程并发推进，
降到约 7 ms，5.8 倍。

这里有个容易写错的地方：**必须先把 N 个环境的动作全部下发，再统一收结果**。如果
在循环里发一个收一个，子进程之间就退化成串行了，等于白开进程。这个坑在本项目
`robotrl/envs/vector_env.py` 的注释里记着。

纯 CPU 上的速度是每秒几千步，所以一次 G1 行走训练要几十分钟——这是本项目把
toy 环境（不依赖物理引擎、秒级）单独拿出来的原因：**调试流程用 toy，正式训练
用真实机器人**。
