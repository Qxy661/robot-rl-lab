# 07 未决问题与风险

一个项目说自己是"完整的"时，读者最该问的是"哪里不完整"。这份清单按严重程度
排，每条写清三件事：**是什么**、**影响什么**、**现在是什么状态**。

它和"路线图"不是一回事。路线图写想做什么，这里写已经知道的窟窿——包括那些
不会崩、不会报错，只会让结论变弱的窟窿。

---

## 一、影响结论的

读本项目任何一张数字表之前，先看这五条。

### 1. 所有性能数字出自一个"站不住"的策略

体积、延迟、回测那三张表用的策略，是 8448 步、约 7 秒训出来的，站住 1.6 秒后
仰面摔倒（就是 README 顶上那个 GIF）。这个策略是"能站住"，不是"会走"。

影响的边界要说清：那三张表比的是**同一个策略的两份实现**（FP32 与 INT8），
所以量化代价的结论成立。但它回答不了"这套框架能不能训出会走的机器人"——那是
另一件事，需要另一种规模的训练。

**状态**：正式预设已经写好（G1 PPO 2000 万步 / 64 环境，Go2 SAC 3000 万步 /
32 环境）。纯 CPU 上是小时级，本机没跑完。README 的当前状态表里把这条标成
"未跑"，而不是含糊地说"训练规模较小"。

### 2. 绝对延迟不可迁移，能迁移的只有比值

这台 CPU 是大小核混合架构。同一个模型、同一份输入，逐个逻辑核测最小延迟，
最快 0.0100 ms、最慢 0.1097 ms——**差近 8 倍**。

所以 README 里"0.0099 ms"这个数，只在"CPU1 上"这一个条件下成立。换一个核、
换一台机器，它都不成立。真正能带走的结论是 FP32 与 INT8 的**比值**（0.85×），
因为两个模型是在同一个核上、交替测出来的。

**状态**：基准脚本默认逐核试探后绑到最快的核，并把核号写进报告（`benchmark_*.json`
的 `cpu` 字段）。要跨机器比较，只比比值。相关实现与实测见
`robotrl/utils/cpu_affinity.py` 的模块文档。

### 3. INT8 的回测结论只在部分 CPU 上成立

这是这条链路里最反直觉的一个坑：**同一份量化文件，同一份输入，onnxruntime 在
某些 CPU 上会算错**，而且错得不小。

发现过程值得记下来，因为它演示了"绿灯"有多容易骗人。一次 CI 上，3.10 那条分支
的两个量化用例报出 0.196 的最大偏差（阈值 0.05），同一次运行的 3.11、3.12 全过。
第一反应是"3.10 的依赖版本不同"——查下来确实不同（3.10 装到 onnxruntime 1.23.2，
另外两个是 1.30.0），但把这套依赖在本机复现，误差照样是 5e-03。**版本不是变量。**

真正的变量是跑在哪个 runner 上：GitHub 的 ubuntu-latest 是一个异构池，同一次矩阵
的三个分支可能落到不同型号的 CPU 上。于是做了一组对照——把同一份文件分别交给
三个"计算方"，看它们互相差多少：

| 运行环境 | CPU | onnxruntime 动态 INT8 | onnx 参考实现 | 静态 QDQ |
|---|---|---|---|---|
| GitHub Actions | Xeon 8370C | 5.14e-03 ✅ | 5.14e-03 ✅ | 2.60e-02 ✅ |
| GitHub Actions | EPYC 9V74 / 7763 | 1.96e-01 ❌ | 5.14e-03 ✅ | 1.70e-01 ❌ |
| 本机 | Core Ultra 7 255H | 5.14e-03 ✅ | 5.14e-03 ✅ | — |

（表里是相对 FP32 的最大绝对偏差，越小越好；FP32 自身的对照是 1e-07 量级。
CI 报的 1.958325e-01 与表里 AMD 那一格逐位相同。）

最后一列只有两个口径，没有参考实现那一栏：onnx 的参考实现跑不了静态量化图
（`DequantizeLinear` 在 opset 17 上它没有实现），所以那一列的 ✅/❌ 只能说"在不在
门限内"，不能说"有没有被忠实执行"。这一格的缺口是个真实的盲区——静态量化这条
路目前只有结构断言盯着（节点数、元数据），数值上没有裁判。

onnx 参考实现是纯 numpy 的，按算子定义逐步算，不经过任何 CPU 核。它和两台 Intel
一致，说明**量化产物本身没问题**；只有那两台 AMD 上，onnxruntime 的 int8 核给出
另一个值。动态与静态两条路都错，两台不同型号的 AMD 给出的错值逐位相同，同一台
机器上多次运行逐位相同——所以不是随机性，是那个核在这类指令集上稳定地算错。

**能说的和不能说的**：三台机器上观察到的分别是"有 VNNI 就对、没有就错"，这是个
相关性，不是已验证的机理——onnxruntime 的内部实现没有查，样本也只有三台。所以
下面这条用例不按"CPU 型号白名单"来判，而是每次现场比一次参考实现。

另有一条排除记录：`per_channel`、图优化级别（all / extended / basic / disable）、
onnxruntime 1.23.2 与 1.30.0，都不改变结论。

**状态**：这是 onnxruntime 的缺陷，不在本项目能修的范围内，所以用例的处置不是
"放宽阈值"而是"把两件事拆开"：

- **一份用例断言量化产物**，判据取参考实现，与机器无关，任何机器上都跑、都严格。
- **一份用例断言运行时的忠实度**，不忠实就跳过，并把 CPU 型号、两个偏差的数、
  以及"这不是本项目的量化流程的问题"写进跳过理由。CI 用 `pytest -rs` 把理由打进
  日志——否则跳过会以绿灯的形式出现，与真正的通过分不开。
- 回测那条会跟着第二条一起跳过：运行时算得不对时，"INT8 回报掉了多少"这个结论
  不成立。

要在目标硬件上取回测结论，就在目标硬件上跑 `scripts/evaluate.py`。这也是本项目的
原意——回测的用处是回答"这块板子上跑得动吗"，本来就不该由 CI 的机器代答。

### 4. 训练的可复现靠约定，不是靠机制

这个坑真实踩过：项目的环境随机源一直是按种子显式构造的（`reset(seed=...)`），
但策略网络的权重来自 torch 的**全局**随机源，而全仓没有一处调用过
`torch.manual_seed`。结果是两份配置完全相同的训练，第一轮评估的回报就已经
不同（实测 48.1 对 46.5），最终权重自然也不同。症状是：训练照常收敛、曲线照常
好看、没有任何报错，只是"照着 README 跑一遍就能得到那组数字"这件事不成立。

已经修的：`robotrl/utils/torch_runtime.py` 加了 `seed_torch`，`scripts/train.py`
与 `examples/toy_train.py` 都在建策略之前调用它。

**还没修的**：这是调用方的责任，不是强制。绕过这两个脚本自己写训练循环的人，
漏掉那一句就会退回到不可复现——而且不会有任何提示。要变成机制，得把种子的
写入挪进策略构造里，代价是"构造一个网络"这种看似纯函数的东西开始有全局副作用。
这个取舍没做，暂时靠这条说明和 docstring 承担。

### 5. KL 阈值现在拦不住小偏差

回测里有一道闸：动作分布 KL 超过 0.1 就报错，而不是照样给个结论。当前两份量化
模型的 KL 都是 0.0000（64 个 bins，1331 个样本）——这个"通过"不等于"没偏"，
只等于"偏得小于一个 bin"。逐样本的 KL 估计本身有约 0.2 的偏差（报告里已扣除），
说明这个估计的分辨率就在同一量级。报告自己也写着"样本偏少，KL 只能看趋势"。

**状态**：阈值留着——它拦得住大偏差，实测触发过一次（KL 均值 0.358、最大维
5.37，同一次回测里的动作最大偏差 0.0536，是当前这份的 5 倍多）。看小偏差要靠
同一张表里的动作 MAE（0.00093 / 0.00127）和最大偏差（0.0070 / 0.0099），这两个
数才是精细的。要提高 KL 的分辨率得加样本量、加密 bins，或者改用别的分布距离。

## 二、限制扩展的

### 6. 配置不支持 include，环境参数有两份

配置加载器只吃一个文件、不做 include（见 `robotrl/utils/config.py`）。代价是
`configs/train/g1_velocity.yaml` 的环境段与 `configs/envs/g1_flat.yaml` 内容重复，
`configs/train/g1_smoke.yaml` 又是前者的复制。改一个环境参数要记得改多处。

之所以还没修：加 include 或者继承会改变配置的加载顺序，而"配置从哪来、被谁覆盖"
一旦变得需要推理，调试成本会转移到每一次改超参上。目前的选择是接受重复，并在
三个文件里都写明这件事。

### 7. ONNX 导出走的是 legacy 导出器

`torch.onnx.export` 的 TorchScript 路径从 torch 2.9 起不再是默认，当前会打
DeprecationWarning。现在导出的是 opset 17，等价校验通过（与 PyTorch 的最大
绝对误差 1.8e-07，容差 1e-05）。

**状态**：等新的 torch.export 导出器在 CPU 上的算子覆盖足够稳再切。切换本身不难，
难的是确认量化链路（动态量化插哪些算子、静态量化的校准数据怎么喂）在新图上
行为一致——那需要重跑一遍整条链并对比。

### 8. 域随机化的范围是照搬的，没有做消融

`envs/events.py` 里推搡间隔、质量偏差这些取值来自常见做法（文献与同类项目的
常用量级），没有在本任务上做过消融。也就是说：不知道其中哪几项真的有用，哪几项
只是让训练变慢。

**状态**：没动。消融实验本身要几十次训练，和"策略还没训出来"是同一个前置条件。

### 9. 楼梯地形没有预设配置

`envs/terrain.py` 支持 flat / rough / stairs，stairs 有单测（台阶高度、助跑段、
顶部平台），但 `configs/` 下没有一份用它的预设，也没训过。

### 10. SAC 没有在真实形态上训练过

SAC 有专门的单测，覆盖 tanh 修正、终止与截断的自举差异、目标网络的更新节奏、
熵温度的自适应，以及在 toy 环境上训通不出现 NaN。Go2 的 SAC 预设
（`configs/train/go2_sac.yaml`）写好了，没跑过。

配对跑 PPO 与 SAC 是项目的特性之一（"同环境多算法对比"），目前只有配置层面对齐了
总步数预算，没有实测数据。

## 三、已知的取舍

这几条不是待修的缺陷，是权衡之后的选择，写出来是为了让读者知道边界在哪。

### 11. 多进程的进程数按逻辑核数取

`default_num_workers` 取 `min(num_envs, cpu_count())`，用的是**逻辑**核而不是物理核，
也不区分大小核。在这台机器上大小核性能差近 8 倍，所以"16 个 worker"不等于 16 份
等量的算力。不做自动调优的理由：猜错了只会更慢，而且慢得没有线索。并行度由配置
里的 `num_envs` 显式给。

### 12. 录制需要 Pillow，是可选 extra

`pip install -e ".[record]"`。不装时 `tests/test_record.py` 整组跳过——这件事本身
是一个风险：跳过会以绿灯的形式出现。所以 CI 装的是 `.[dev,deploy,record]`，
那里会真跑。本地只装 `.[dev]` 的人看到的是 14 个测试没跑，而不是 14 个测试通过。

### 13. 没有覆盖率门槛，没有类型检查

`pytest-cov` 装了，但没有设 `fail_under`；类型标注写得很密（全仓
`from __future__ import annotations`，公开接口都有标注），但没有接进 CI，也没有
`py.typed`。换句话说：类型标注现在是给人看的文档，不是被机器保证的约束。

加到 CI 的成本不高，没做的原因是它会把"当前这一版"冻结成门槛，而下一条要动
的地方（真机后端、新的地形）还没定型。

### 14. 真机与 NPU 只有接口没有实现

`PolicyEngine.register_backend` 是留的口子。RKNN / BPU / TensorRT 一个都没接，
也没在任何一块真实硬件上跑过。README 的当前状态表里这条标的是"未做"，
不是"进行中"。

## 怎么用这份清单

- 想评估这个项目**能不能解决你的问题**：看第一节。那五条决定了你看到的数字
  在什么条件下成立。
- 想接着往下做：看第二节。那是按"投入产出比"排的——第 6 条改配置加载，第 10 条
  跑一次 SAC，都不需要新的基础设施。
- 想判断作者是不是在夸大：数一下这份清单有几条，再看看 README 里的当前状态表。
  两份文档对同一件事的说法必须一致，不一致就是有问题。
