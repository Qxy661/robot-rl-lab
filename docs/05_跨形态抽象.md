# 05 · 跨形态抽象

这一章讲本项目的一个核心设计：**同一套代码怎么同时支持三种不同的机器人**。
更重要的是，这套机制让你能加进第四种——包括无人机、车辆这些非足式形态。

## 问题在哪

四足机器人有 12 个关节，G1 人形有 29 个。这带来两个麻烦。

第一，**观测和动作的维度不一样**。四足的观测是 `12 + 3×12 = 48` 维，G1 是
`12 + 3×15 = 57` 维。如果代码里到处写死维度，换机器人就要改几十处。

第二，**同一个概念的实现不一样**。四足是蹲伏站姿、G1 是直立站姿；四足没有腰关节、
人形有；四足的"足端"有四个、双足有两个。这些差异散布在奖励函数、终止条件、
初始姿态里。

最糟的做法是写两个环境类——`Go2Env` 和 `G1Env`，共用的部分复制粘贴。这样改一处
奖励函数要同步改两个地方，加第三种形态要写第三份。**这是绝大多数机器人 RL 项目
在加第二种机器人时崩掉的地方。**

## 解决思路：把"变化的部分"抽成数据

本项目的做法是把所有因机器人而异的东西**抽成一份数据**，代码只读这份数据、
不硬编码任何具体机器人的细节。

这份数据就是 `RobotSpec`：

```python
@dataclass(frozen=True)
class RobotSpec:
    name: str                          # "g1"
    morphology: Morphology             # BIPED / QUADRUPED / POINT
    menagerie_dir: str                 # 模型文件在哪
    controlled_joints: tuple[str, ...] # 控制哪些关节，顺序即动作顺序
    default_angles: tuple[float, ...]  # 默认站姿
    pd_kp: tuple[float, ...]           # 位置环增益
    pd_kd: tuple[float, ...]           # 阻尼
    torque_limits: tuple[float, ...]   # 力矩上限
    action_scale: float | tuple = 0.25 # 动作缩放
```

三种形态的差异全部收在这份数据里。环境层的任务是这么写的：

```python
n_dof = self.spec.n_dof                       # 不写死 12 或 15
target = self.spec.default_angles_array + self.spec.action_scale_array * action
```

**没有任何一处假设机器人长什么样。**

## 换机器人要改什么

改配置里的一个字符串：

```yaml
env:
  robot: go2      # 改成 h1、g1
```

具体来说，这一个字段会连锁触发的改动是：

- 加载对应的 MuJoCo 模型文件
- 动作维度从 12 变成 19 或 15
- 观测维度随之改变
- 默认站姿、PD 增益、力矩上限换成对应的值
- 奖励函数自动按新形态的关节数计算

策略网络的输入输出维度也要跟着变——这由训练脚本在建立网络时从环境读取维度，
不需要手工配置。

## 形态分类：什么时候需要知道"是哪种机器人"

有些逻辑确实需要知道机器人的大类。比如"足端接触奖励"在两足和四足上算法不同，
"步态对称性"惩罚只对足式有意义。

这时候用 `morphology` 字段判断：

```python
if spec.morphology is Morphology.QUADRUPED:
    num_feet = 4
elif spec.morphology is Morphology.BIPED:
    num_feet = 2
```

关键是**判断的粒度是"大类"而不是"具体型号"**。任务代码可以问"这是四足吗"，
但不该问"这是 Go2 吗"。前者加新四足机器人不用改代码，后者每加一个型号都要改。

`POINT` 这个分类是留给非足式形态的——质点、无人机、车辆都归进去。toy 环境用的
就是它，任务层据此跳过一切与足式相关的奖励项。

## 冻结关节：一个设计上的例子

G1 有 29 个自由度，但本项目只控制 15 个（腿 12 + 腰 3），手臂不管。

不控制的关节不能放着——在地心引力下会瘫软下来乱甩。做法是照样给它们一个目标角度
（模型里定义好的默认姿态），让 PD 控制器锁住。

这件事的实现方式体现了抽象的价值。一个直接的做法是修改 MJCF 文件，把手臂关节的
执行器删掉。但那样就把 G1 的特殊处理和模型文件绑死了，将来想控制手臂还得再改回来。

本项目的做法是：`RobotSpec` 只列**被控制的关节**，其余关节由 `loader.py` 在加载时
自动算出它们的执行器索引和保持目标。环境层对这两种关节一视同仁——都是写一个目标
角度到执行器，区别只是目标来自策略还是来自模型。

结果是：**想控制手臂，只需在 `g1.py` 的 `controlled_joints` 里加几行**，其他代码
一行都不用动。

## 加一种新形态

假设要加 Unitree B2 四足（Menagerie 里有）。三步：

**第一步**，新建 `robotrl/assets/b2.py`：

```python
from robotrl.assets.spec import Morphology, RobotSpec, register

B2_SPEC = register(RobotSpec(
    name="b2",
    morphology=Morphology.QUADRUPED,
    menagerie_dir="unitree_b2",
    controlled_joints=(...),      # 从 b2.xml 里抄关节名
    default_angles=(...),         # 从 keyframe 抄
    pd_kp=(...),
    pd_kd=(...),
    torque_limits=(...),
))
```

**第二步**，在 `robotrl/assets/__init__.py` 里加一行 import，触发注册。

**第三步**，在 `scripts/fetch_assets.py` 的 `SUBDIRS` 里加上 `unitree_b2`，
然后运行它拉模型。

然后就可以直接用了：

```bash
python scripts/train.py --config configs/train/go2_velocity.yaml --set env.robot=b2
```

**整个过程中，环境层、算法层、部署层的代码一行都不用改。**

## 非足式形态：扩展口在哪

项目现在做的都是足式，但框架本身不绑足式。加无人机大概是这样：

- 写一份 `DroneSpec`（或复用一个 `RobotSpec`，无人机也有旋翼转速这些"关节"）
- 写一个 `DroneEnv(BaseEnv)`，填 8 段管线——推力分配代替 PD，六自由度刚体动力学
  代替关节运动，这些交给 MuJoCo 的模型文件
- 在注册表里注册 `make("Drone-Hover")`

部署层完全复用：策略还是"观测进、动作出"，导出还是 ONNX，量化、基准、回测的
流程一模一样。

这也是这个项目定位的一部分——**训练-部署这条链路本身是通用的**，换一个领域，
换的是环境，不变的是流程。把这条链路走通一遍，比只会调某一个机器人更有迁移价值。

## 抽象的成本

诚实地说，这种抽象是有代价的：

- 多了一层间接。读任务代码时要同时看代码和 `RobotSpec` 才能知道具体数值。
- 有些性能优化做不了。比如把关节数写死能让编译器做更好的优化，走配置文件就
  只能运行时决定。
- 前期设计成本高。契约没定好，后面加形态时会发现处处是坑。

判断标准是**变化频率**。如果项目只会有一种机器人，抽象就是负担；如果预期会加
第二、第三、第四种，抽象带来的收益会迅速超过成本。机器人 RL 这个领域，后一种
情况是常态——同一个方法要在四足、人形、机械臂上都验证一遍，才能说是通用方法。
