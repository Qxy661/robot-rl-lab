# 06 · 部署与量化

训练完一个策略，它只是一个 PyTorch 的权重文件。要让它真的在机器人上跑，还有一段
路要走。这一章讲这段路，以及本项目和同类项目差别最大的地方。

## 为什么不能直接把 PyTorch 搬上去

最直接的想法是把 PyTorch 装在机器人的主控板上，加载权重直接跑。这条路走不通，
原因有几个：

**体积**。PyTorch 加上依赖有几个 GB，一块嵌入式板子的存储和内存都很紧张。

**依赖**。装 PyTorch 意味着装一整套 Python 科学计算栈。而机器人主控常常是 C++
写的实时程序，只认一个轻量的推理库（ONNX Runtime、TensorRT、板卡厂商的 SDK）。

**确定性**。实时控制里不希望推理库在后台做内存回收或者线程调度，PyTorch 不是
为这种场景设计的。

所以中间需要一个交换格式：**ONNX**。

## ONNX：神经网络的通用格式

ONNX（Open Neural Network Exchange）是一种描述计算图的格式。它不是推理引擎，
而是一份"这个网络由哪些算子、按什么顺序连起来"的说明书，任何推理引擎都能读。

导出过程把一个 PyTorch 模型翻译成这份说明书：

```python
torch.onnx.export(policy, dummy_input, "policy.onnx")
```

导出的图是静态的——训练时用的自动求导、动态控制流都不在图里，剩下的就是纯计算。
这是好事：端侧只需要按顺序执行算子，不需要任何训练相关的开销。

### 自包含：把预处理也放进图里

这里有一个容易被忽略的坑。

策略网络的输入不是原始观测，而是**归一化之后的观测**——训练时统计的均值和方差
会被减掉、除掉。如果只导出网络本体，那么端侧代码必须自己实现一遍这段归一化：

```python
# 端侧要写的东西
obs_normalized = (obs - mean) / std
action = model(obs_normalized)
```

问题在于 `mean` 和 `std` 要单独从训练侧传过来，两边对不上（比如顺序搞错、维度
搞错）是很容易发生的事，而且**出错了不报错，只是机器人动作不对**。

本项目的做法是把归一化做进网络本身：

```python
class Policy(nn.Module):
    def __init__(self, obs_dim, action_dim):
        self.register_buffer("obs_mean", torch.zeros(obs_dim))
        self.register_buffer("obs_std", torch.ones(obs_dim))

    def forward(self, obs):
        normalized = (obs - self.obs_mean) / (self.obs_std + 1e-8)
        return self._policy_forward(normalized)
```

因为 `obs_mean` 和 `obs_std` 是注册的 buffer，它们会跟着 `state_dict` 一起存取，
导出 ONNX 时也自然变成图里的常量节点。**端侧拿到的就是一个"裸观测进、动作出"的
完整模块**，不需要任何预处理代码，也就没有两边对不上的问题。

## 等价校验：先确认导出没搞砸

导出之后、量化之前，有一件事必须先做：**验证 ONNX 的输出和 PyTorch 的输出一致**。

```
输入同一批观测
    PyTorch → 动作 A
    ONNX    → 动作 B
    比较 A 和 B，最大误差应该小于 1e-5
```

误差超了说明导出过程出了问题——可能是算子不支持被替换了、可能是某个 buffer 没
进图、可能是数据类型被转换了。

**为什么这一步不能跳过**：后面的量化会引入它自己的误差。如果导出的图本身就是错的，
那么量化之后测出来的性能下降，你分不清是量化的锅还是导出的锅。先把导出校验干净，
后面的数字才有意义。

这一步在同类项目里经常被省略，本项目的 `robotrl/deploy/equivalence.py` 专门做它。

## 量化：用更少的位数表示数字

神经网络的参数默认是 32 位浮点数（FP32）。量化把它换成 8 位整数（INT8），
存储直接降到四分之一。

加速的来源不只是省内存。整数的乘加运算在多数硬件上比浮点快得多，而且能更好地
利用 SIMD 指令。

但"量化更快"这句话里藏着一个条件：**快是因为那块硬件有整数运算单元**。带了
INT8 加速单元的 NPU 上，这个结论成立；通用 CPU 上跑一个小网络，结论可能恰好
反过来——本项目实测就是反的，见后面的《实测：这颗 CPU 上量化没让网络变快》。

代价是**精度**。INT8 只能表示 256 个不同的值，覆盖一个范围，范围之外的数只能
截断。所以量化需要一个映射：

```
真实值 = 缩放系数 × 整数值 + 零点偏移
```

缩放系数决定了精度和范围的权衡——范围大则精度低。

### 两种量化方式

**动态量化**（dynamic）：权重量化成 INT8，激活值在推理时**动态**计算缩放系数。
不需要校准数据，一行代码就能做：

```python
from onnxruntime.quantization import quantize_dynamic
quantize_dynamic("policy.onnx", "policy_int8.onnx")
```

代价是推理时多了一点计算缩放系数的开销。

**静态量化**（static）：权重和激活值都预先量化。需要一批**校准数据**——拿真实的
观测喂进去，统计每一层激活值的分布，据此定好缩放系数。

精度更好、速度更快，但流程更重：要准备校准集，还要处理某些算子不支持量化的问题。

本项目两种都支持（`DeployConfig.quant_format`），默认用动态量化，因为它不需要
准备额外的数据，开箱即用。

## 延迟基准：怎么测才有意义

量化之后要量出到底快了多少。这件事看起来简单，但有几个必须处理的地方。

**先预热**。第一次推理总是慢的：CPU 要升频、缓存是冷的、内存要分配。不预热直接
测，前几次的数据会把统计量拉偏，尤其是 p99。

```python
for _ in range(warmup):       # 预热 50 次，数据丢弃
    session.run(None, {input_name: obs})
```

**报分位数，不只报平均**。控制系统的实时性要求是"最坏情况不能超时"，所以关心的
是 p95、p99 而不是平均值。一个平均 2ms 但 p99 达到 20ms 的推理，在 20ms 的控制
周期里会周期性丢帧。

**说明线程数**。单线程测的是纯算子延迟，多线程测的是吞吐。两个数字含义不同，
混在一起对比没有意义。

**结论取最小值，不取均值**。干扰只会让一次测量变慢，不会让它变快，所以所有样本
里最小的那几次最接近真实的计算耗时。均值里混着被干扰拉长的样本，分位数也一样。
微秒级的测量尤其如此：同一台机器上同一份模型，p50 能在 0.010–0.032 ms 之间跳，
而 min 在六轮交替测量里稳定到四位有效数字。本项目把 min 当作加速比的头号依据，
p99 保留作参考。

**配对测量**。"先测完 FP32、再测 INT8"这种串行做法有个致命问题：两次测量落在
不同的机器状态里。降频、后台进程、内存回收都会让后测的那个吃亏或占便宜，测出来
的加速比可能整个是假的。正确做法是**交替测**——每轮里两个模型各测一次，轮内
条件一致，再看各轮比值的分布是否稳定。

**波动超过差异就拒绝下结论**。各轮比值必然有波动。如果波动的幅度已经超过了要测
的差异本身，那么任何"1.35×"之类的结论都是噪音。这时候报告该直接写"本机分辨不
出来"，而不是照常给一个两位小数。

这几条加上预热和分位数，就是 `robotrl/deploy/benchmark.py` 的默认行为。

## 回测：量化之后策略还能用吗

这是最关键的一步，也是同类项目里几乎没人做的一步。

延迟降低了，但如果量化把策略的输出搞乱了，再快也没用。所以要**让量化前后的两个
策略在完全相同的条件下跑一遍，对比结果**。

本项目 `robotrl/deploy/evaluate.py` 做的事：

- 用相同的随机种子初始化环境，保证两个策略面对**完全相同的初始状态和指令序列**
- 各跑若干完整回合，记录回报和回合长度
- 逐步对比同一状态下的动作差异：平均绝对误差、最大偏差
- 比较两个动作分布的 KL 散度

最后输出这样一组数：

```
                         FP32        INT8        差异
平均回报                 42.3        41.8        -1.2%
回合长度                 198         196         -1.0%
动作 MAE                 —           0.0031      —
动作最大偏差              —           0.021       —
与 FP32 动作的 KL         —           0.014       —
推理延迟 p50 (ms)        1.82        0.61        -66%
```

有了这张表，才能回答"这个量化方案能不能用"：**如果 KL 散度小于阈值、回报下降
在可接受范围内，就可以用**。如果掉得太多，说明需要换静态量化、或者对敏感层
保留 FP32（混合精度）。

（上表是格式示意，本项目实测的数字在下一节。）

这里还有一个细节：**逐段做误差归因**。观测契约把观测分成若干段，可以分别统计
每一段受量化的影响。如果发现某一维（比如关节速度）特别敏感，调优就有方向了。

这一步依赖 `robotrl/contracts.py` 里的观测契约——按名字取某一段的切片。

## 实测：这颗 CPU 上量化没让网络变快

上面每一步本项目都跑过。下面是在一台 Intel Core Ultra 7 255H 上、onnxruntime
CPU 后端、单线程 batch 1 的实测结果。任务用 G1 速度跟踪，15 个受控关节，策略
观测 57 维；对照的是**同一个策略的两份实现**，所以绝对值不构成性能声明。

| | FP32 | INT8 动态 | INT8 静态 |
| --- | --- | --- | --- |
| 文件体积 | 199.3 KB | 61.0 KB（3.27×） | 61.0 KB（3.27×） |
| min 延迟 | 0.0100 ms | 0.0118 ms | 0.0118 ms |
| 加速比（按 min） | 1.00× | 0.91× | 0.84× |
| 仿真回测回报（20 回合） | 63.157 | 62.997（−0.25%） | 63.141（−0.02%） |
| 逐维动作 MAE | — | 0.0013 | 0.0019 |

三件事值得单独说。

**体积的收益是确定的。** 3.27 倍。INT8 存的是整数，这是算术上的必然，跟硬件
无关，对端侧存储和内存带宽都是实打实的。

**延迟的收益是负的。** 两份量化模型都比 FP32 慢 10%–19%。原因不神秘：量化把
矩阵乘换成了整数版本，但周围多出一圈转换算子——动态量化每层要现算激活值的缩放
系数（图里 3 个 `DynamicQuantizeLinear`），静态量化把图切成一堆
`QuantizeLinear` / `DequantizeLinear` 片段（6 + 12 个节点）。这个网络只有几万
参数，算力从来不是瓶颈，省下的那点乘加抵不过多出来的算子调度。**加速比是硬件
属性，不是量化方案的属性。**

**精度几乎没损失。** 回报掉 0.02%–0.25%，逐维动作平均偏差 0.0013–0.0019，最大
偏差 0.0135——动作本身以 0.1 为量级，这个偏差不影响行为。

所以"要不要量化"没有统一答案，取决于你缺什么：缺存储就直接量化；缺延迟，先按
上面的方法量一遍再决定。把这条链做成一条命令，就是为了让这个决定有数可依，
而不是靠"量化更快"这个经验法则。

还有一条前提要写在这里：**"精度几乎没损失"这个结论只在"运行时算得对"的机器上
成立**。已知在部分 CPU 上，onnxruntime 的 int8 核会给出错值——同一份量化文件、
同一份输入，与参考实现最大差 0.196，比量化本身引入的误差大两个数量级。这不是
本项目量化流程的问题（纯 numpy 的参考实现与另一批 CPU 都算得对），但它意味着
"量化代价有多大"这个问题必须在自己那块板子上量一遍，而量它的方法就是本节这张表。
判据、现场记录与用例里的处置见 [07 未决问题与风险](07_未决问题与风险.md) 第 3 条。

## PolicyEngine：为换硬件留的口子

本项目不绑定任何具体硬件，但真实部署总要落到某块板子上。所以抽象一层：

```python
class PolicyEngine(ABC):
    def load(self, path): ...          # 加载模型
    def infer(self, obs): ...          # 单次推理
    def latency_stats(self): ...       # 延迟统计
```

目前实现了 `OnnxRuntimeEngine`（CPU 上跑，跨平台）。要接别的后端，只需要实现
同一个接口：瑞芯微 RK3588 的 RKNN、地平线 BPU、NVIDIA 的 TensorRT 都是这么接。

抽象的价值在于**调用方不用改**：训练脚本、回测脚本、基准脚本都只认 `PolicyEngine`，
换后端对它们透明。

## 这条链路的意义

把上面这些串起来，就是本项目的完整闭环：

```
训练 → 策略 → ONNX → 等价校验 → INT8 量化 → 延迟基准 → 仿真回测
```

每一步都有明确的产物，每一步都能单独验证。

之所以花力气把后三步做完整，是因为**这是仿真和真机之间最容易被跳过、又最不该
跳过的一段**。开源社区里大量的机器人 RL 项目停在"导出 ONNX"，读者拿不到任何
关于部署代价的信息：量化会掉多少精度？延迟够不够 20ms 的控制周期？没人说。

这部分工作不依赖具体机器人，也不依赖具体硬件——换任何策略、任何设备，流程都是
一样的。**它是这个项目里迁移性最强的部分**。

## 动手试试

```bash
# 跑通 toy 环境的完整链路（分钟级）
python examples/toy_train.py

# 单独跑各步骤。--run-dir 指向训练产物目录，输入输出路径由各脚本自己推导
python scripts/export.py    --run-dir runs/g1_dev
python scripts/quantize.py  --run-dir runs/g1_dev --mode static
python scripts/benchmark.py --run-dir runs/g1_dev --repeats 5
python scripts/evaluate.py  --run-dir runs/g1_dev --markdown
```

留意 `equivalence.py` 报出的误差，以及 `evaluate.py` 报出的 KL 散度。这两个数字
是判断一个量化方案能不能用的依据。

基准那一步建议多跑几轮（`--repeats 5` 以上），并且**故意开着浏览器或者别的重活
跑一次**，观察各轮比值波动起来之后报告怎么写。这是最快理解"为什么不能报均值"
的办法——安静机器上的数字看起来总是很干净，干净到让人以为测一次就够了。
